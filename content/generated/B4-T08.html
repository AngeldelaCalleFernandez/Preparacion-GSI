HTTP y su ámbito

Resumen

HTTP es una familia de protocolos de nivel de aplicación, sin estado y basada en intercambios de petición y respuesta. Presenta a los clientes una interfaz uniforme e independiente de cómo esté implementado el servicio, con semántica extensible y mensajes que describen la interacción.

Mensajes y semántica

Explicacion

Cada mensaje HTTP es una petición o una respuesta. El cliente envía una petición que incluye un método y un objetivo; el servidor interpreta esa intención respecto del recurso y devuelve una respuesta que incluye un código de estado. Los mensajes pueden transportar campos, contenido y campos finales, cada uno con una función semántica diferenciada.

Recursos y representaciones

Resumen

El objetivo de una petición se denomina recurso y normalmente se identifica mediante un URI. HTTP intercambia representaciones del estado de ese recurso: datos acompañados por metadatos, no necesariamente el recurso en sí mismo.

Métodos HTTP

Resumen

El método comunica la intención de la petición y forma parte de la semántica uniforme de HTTP. Este piloto no enumera ni explica métodos concretos porque los localizadores detallados correspondientes todavía no están verificados en el catálogo técnico.

Códigos de estado

Resumen

La respuesta incluye un código de estado que permite al cliente interpretar el resultado y decidir su siguiente acción. La clasificación y el significado de códigos concretos quedan pendientes de localizadores técnicos adicionales.

Campos HTTP

Explicacion

Las peticiones y respuestas pueden incluir campos con modificadores, información de participantes y metadatos de la representación o del recurso. Su significado depende del contexto del mensaje. No se desarrolla aquí el catálogo de campos individuales.

Intermediarios

Explicacion

HTTP permite cadenas de intermediarios entre agente de usuario y servidor de origen. RFC 9110 distingue tres formas habituales: proxy, gateway o pasarela, y túnel. Un mismo componente puede asumir distintos papeles según la petición; por ello conviene separar el papel desempeñado de la identidad del programa.

HTTPS y su relación con TLS

Derivado

HTTP define la semántica de aplicación y puede usar distintas capas de transporte o sesión. TLS es independiente del protocolo de aplicación y establece claves para proteger datos de aplicación. En este piloto, HTTPS se estudia como la combinación conceptual de HTTP con un canal TLS, sin desarrollar certificados, PKI ni la selección concreta del transporte.

TLS 1.3: objetivos y componentes

Resumen

La visión general de TLS 1.3 separa el establecimiento de claves mediante el handshake y la protección posterior de los datos de aplicación. El protocolo contempla autenticación del servidor y, opcionalmente, del cliente dentro del intercambio descrito. Los detalles de algoritmos y certificados quedan fuera de esta cobertura parcial.

Handshake de TLS 1.3

Explicacion

El handshake o protocolo de establecimiento intercambia mensajes para acordar parámetros criptográficos, autenticar a las partes según el modo utilizado y obtener material de claves compartido. Tras ese intercambio, las partes pueden proteger datos de aplicación con las claves resultantes.

Protección de registros

Explicacion

TLS organiza el tráfico protegido en registros. Las claves derivadas durante el establecimiento se usan para proteger los datos transmitidos; la visión general también diferencia fases iniciales del intercambio y datos de aplicación posteriores. Este resumen no reproduce formatos binarios ni algoritmos del estándar.

Glosario breve

Resumen

  • Método HTTP: componente de la petición que expresa su intención.
  • Código de estado: componente de la respuesta que comunica su resultado semántico.
  • Intermediario: participante situado entre agente de usuario y servidor de origen, como proxy, pasarela o túnel.
  • Handshake: intercambio de TLS que acuerda parámetros y material de claves.
  • Registro TLS: unidad en la que TLS organiza y protege el tráfico.
